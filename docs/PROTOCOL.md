# Multiplayer HTTP and WebSocket protocol (v1.15 source)

**Authority:** `server/worker.js` and the `Net` plus `net*` handlers in `game/index.html`. This reference describes current messages; it is **not** a versioned or security-hardened public API contract.

## Endpoints

| Method | Route | Request | Response/behavior |
|---|---|---|---|
| `GET` | `/health` | none | JSON `{ok:true, game:"scorched-tanks", v:2, app:"1.15"}` at this source revision |
| `POST` | `/api/room` | JSON `{public?:boolean,max?:number}` | `{code:"ABCD"}`; max bounded 2–6, default 4; retries collisions eight times |
| `GET` | `/api/room/ABCD` | none | `code,status,public,max,players` or `404` |
| WebSocket | `/ws/quick?name=&pid=&ver=` | query args | Lobby matchmaking queue |
| WebSocket | `/ws/room/ABCD?name=&pid=&ver=` | query args | Room roster, signaling, relay |
| `GET` | `/`, `/join/ABCD` | none | Landing/invite page |
| `GET` | `/play` | none | Browser game HTML |
| `GET` | `/download`, `/ScorchedTanks.apk` | none | Published APK binary |
| `GET` | `/.well-known/assetlinks.json` | none | Android App Links association |

Room codes contain four letters from `ABCDEFGHJKLMNPQRSTUVWXYZ` when generated by the server. Server room routing accepts four alphabetic characters and canonicalizes to uppercase. `name` is sanitized/truncated for roster display; `pid` is supplied by the caller; `ver` is display metadata, not negotiation.

## WebSocket envelope

A client sends JSON with `t` to Room:

| Client `t` | Payload | Server behavior |
|---|---|---|
| `ping` | none | `pong` |
| `relay` | `{d, to?}` | Broadcasts `{t:"msg",from:pid,d}`, or targets `to` |
| `start` | none | Host only; sets room status `playing`; server currently allows one socket |
| `end` | none | Host only; moves room back to `lobby` and removes snapshot |
| `snap` | `{d}` | Host only; persists migration snapshot |
| `public` | `{v:boolean}` | Host only; toggles room discovery |
| `kick` | `{pid}` | Host only; disconnects/removes another player |

Room sends: `hello`, `roster`, `msg`, `host`, `err`, `pong`. `roster` contains `code,host,status,public,max,players:[{pid,name,seat,ver,on}]`. `host` includes `pid,snap` when host changes. The Lobby sends `queue` (count + countdown) and `matched` (room code); the Lobby also accepts `cancel`.

## Gameplay envelope inside `relay.d`

Game messages use a second discriminator, `k`. Client listeners recognize:

| `d.k` | Primary fields | Purpose |
|---|---|---|
| `cfg` | `cfg` | Host distributes lobby settings and selected map |
| `begin` | `seed,cfg,players` | Host starts the online match |
| `needState` | none | Peer requests authoritative state |
| `state` | `d,why,win?` | Host sends serialized match; `why` includes `sync,turn,round,over,end` |
| `aim` | `ti,angle,power,weapon` | Turn-owner aim |
| `fire` | `ti,angle,power,weapon,seed,contact,guide` | Replicated shot simulation |
| `item` | `ti,item` | Use consumable |
| `move` | `ti,x,y,fuel,fi,hp` | Replicate tank movement |
| `shopOpen` | `round` | Open simultaneous shopping |
| `shop` | `pid,round,cash,stock,items` | Player's submitted shop result |
| `shopReady` | `round,pids` | Host rebroadcasts completion roster |

Game messages are accepted by client-side handlers with varying sender/turn validations. The Room DO does **not** authorize the contents of `d`. Host-side shop validation checks lengths, integer/nonnegative quantities and cash bounds, **not** an independent reconciliation of purchases against per-item prices. Do not treat this as anti-cheat protection.

## Room and reconnect behavior

- Client stores `st-pid`, reconnects up to five times with exponential delay and pings every 20 seconds.
- Existing room roster entries are matched by caller-provided `pid`; an existing socket for that pid is replaced.
- Room host is selected from live sockets; if it disconnects, Room announces the replacement and forwards the last `snap`.
- Host snapshots are saved when broadcasting `turn` or `round`. They are not a complete event log or durable authoritative server game.
- After a disconnect, an absent human is temporarily controlled by a CPU on the host; a reconnect triggers state transfer.
- Server `Room` persists roster/snapshot in Durable Object storage. The `Lobby` queue and public-room index are memory-resident.

## Security and compatibility contract

1. Room codes are discoverable/guessable sharing identifiers, **not secret bearer authentication**. Anyone with a code may attempt to join.
2. `pid` is unverified; another client can present the same identifier. Protecting accounts, purchases and ranked gameplay would require real server-side identity.
3. No server-enforced turn authority or server-side physics/economy reconciliation exists for relayed gameplay. Treat players as mutually trusted for casual games.
4. The general JSON API sends CORS `*`; there is no documented authentication, rate limiting or abuse mitigation in the checked-in code.
5. Clients with different versions may connect with only UI warnings. Test interoperability or add explicit protocol version gating before breaking changes.
6. Do not log or publish room snapshots, signing credentials or private player information. Limit untrusted payload sizes and validate schemas before adding public-facing features.
